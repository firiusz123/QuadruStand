# What the network sees and what it outputs (Spot flat-terrain velocity task)

Applies to `QuadruStand-Velocity-Flat-Spot-v0`. At this stage the task inherits Isaac Lab's
`SpotFlatEnvCfg` unchanged, so everything below is defined upstream. Any later change to observations or
actions (Plan 03) must update this document.

Sources (all under `~/tools/nvidia/IsaacLab/source/`):

| What | File |
|---|---|
| Observation / action / command config | `isaaclab_tasks/isaaclab_tasks/contrib/velocity/config/spot/flat_env_cfg.py` |
| Observation functions | `isaaclab/isaaclab/envs/mdp/observations.py` |
| Action processing | `isaaclab/isaaclab/envs/mdp/actions/joint_actions.py` |
| Robot (joints, default pose, actuators) | `isaaclab_assets/isaaclab_assets/robots/spot.py` |
| Runner / network config | `isaaclab_tasks/.../spot/agents/rsl_rl_ppo_cfg.py` |
| Wrapper between env and rsl_rl | `isaaclab_rl/isaaclab_rl/rsl_rl/vecenv_wrapper.py` |

## Summary

```
                        48 numbers                                     12 numbers
 environment ───────── observation ───────►  ACTOR  (MLP 48→512→256→128→12) ───────► action
 (Spot in sim)   (the "policy" obs group)                                           (joint offsets)
                              └──────────►  CRITIC (MLP 48→512→256→128→1)  ───────► state value
                                                                                    (training only)
```

- The actor and the critic both receive the **same** 48-number vector. There is no separate "privileged"
  observation group in this task. The input layers of both networks in a saved checkpoint are `(512, 48)`.
- The actor outputs **12 numbers**, one per leg joint.
- The critic outputs **1 number**, the estimated value of the current state. It is used only for
  training and is not part of the deployed policy.
- Observation normalisation is off (`obs_normalization=False`) and `clip_actions` is `None`. The raw
  values go in, and the raw network output comes out.
- One network evaluation happens every environment step. A step is `decimation × sim.dt =
  10 × 0.002 s = 0.02 s` (50 Hz).
- All values are batched: with `--num_envs N` every tensor has `N` rows, and the shapes below are per robot.

## Input: the 48-dimensional observation

Defined in `SpotObservationsCfg.PolicyCfg`. The terms are concatenated in this exact order
(`concatenate_terms = True`):

| Index | Term | Dim | Meaning | Unit / frame |
|---|---|---|---|---|
| 0–2 | `base_lin_vel` | 3 | Linear velocity of the body (x, y, z) | m/s, body frame |
| 3–5 | `base_ang_vel` | 3 | Angular velocity of the body (roll, pitch, yaw rates) | rad/s, body frame |
| 6–8 | `projected_gravity` | 3 | Direction of gravity expressed in the body frame. This is how the network knows the body's tilt. Upright means roughly (0, 0, −1). | body frame |
| 9–11 | `velocity_commands` | 3 | The commanded velocity the robot should follow: (v_x, v_y, yaw rate) | m/s, m/s, rad/s |
| 12–23 | `joint_pos` | 12 | Joint positions **relative to the default pose** (position minus default) | rad |
| 24–35 | `joint_vel` | 12 | Joint velocities relative to default (default is 0, so effectively the raw velocity) | rad/s |
| 36–47 | `last_actions` (term name `actions`) | 12 | The raw network output of the **previous** step | unitless |

Total: 3 + 3 + 3 + 3 + 12 + 12 + 12 = **48**.

Notes on individual terms:

- **`velocity_commands`.** This is how the task tells the policy where to go. It is not measured, it is
  generated by `UniformVelocityCommandCfg` (`SpotCommandsCfg`):
  - Ranges: `lin_vel_x ∈ [−2, 3]` m/s, `lin_vel_y ∈ [−1.5, 1.5]` m/s, `ang_vel_z ∈ [−2, 2]` rad/s.
  - A new command is drawn every 10 s.
  - 10 % of the environments are "standing" environments (`rel_standing_envs = 0.1`), whose command is zero.
- **`joint_pos` and `joint_vel`.** The "relative to default" part matters. The default pose is the `init_state` in
  `SPOT_CFG`: hip-x ±0.1 rad (left +, right −), front hip-y 0.9, hind hip-y 1.1, knees −1.5. A network
  output of zero therefore means "stay in the default pose".
- **`last_actions`.** Feeding the previous action back in lets the policy see its own last command. This is
  also what the `action_smoothness` penalty relates to.
- **Noise is defined but not applied.** The terms carry uniform noise (for example ±0.1 on velocities), but
  the group sets `enable_corruption = False`, so training currently runs on clean observations. This is
  relevant for sim-to-real, where real sensors are noisy.
- **Joint order.** The 12 joint entries follow the simulator's internal joint ordering, the same for
  observations and actions. I did not verify the order from the source. To print it:
  `env.unwrapped.scene["robot"].joint_names` (needs a created environment).
- **Sim-to-real note.** `base_lin_vel` is not directly measured on a real robot. A deployed policy needs
  a state estimator to provide it. The other terms come from the IMU and the joint encoders.

## Output: the 12-dimensional action

The actor MLP (`48 → 512 → 256 → 128 → 12`, ELU activations in the hidden layers) outputs 12 numbers.
They are mapped to the robot by `SpotActionsCfg`:

```python
joint_pos = JointPositionActionCfg(asset_name="robot", joint_names=[".*"], scale=0.2, use_default_offset=True)
```

For each of the 12 leg joints, in `process_actions` (`joint_actions.py`):

```
target_joint_position = default_joint_position + 0.2 × network_output
```

- `joint_names=[".*"]` means all joints of the robot, which here is the 12 leg joints (the network's 12 outputs
  match). A network output of 1.0 therefore moves a target 0.2 rad away from the default pose.
- The result is sent as a **position target** (`set_joint_position_target`). It is not a torque.
- The robot's actuators then turn the target into torque. `SPOT_CFG` defines PD actuators with
  stiffness 60 and damping 1.5, and a random delay of 0 to 4 physics steps (0–8 ms). Hip actuators are limited
  to 45 N·m, and knee torque limits come from a lookup table.
- The 10 physics steps in each environment step all use the same target.

### What the actor really produces during training

The actor is a Gaussian policy (`GaussianDistributionCfg(init_std=1.0)`). The MLP output is the **mean** of a
12-dimensional normal distribution, and there is a separate learned standard deviation (`std_param`, shape
`(12,)`, one value per joint, independent of the observation). While training, an action is **sampled**
from this distribution, which provides exploration. In evaluation or deployment, the **mean** is used, so the
policy is deterministic.

## Critic output

The critic MLP (`48 → 512 → 256 → 128 → 1`) outputs one scalar per robot: the predicted discounted
future reward from the current state. PPO uses it to compute advantages (`gamma = 0.99`, `lam = 0.95`). It is
discarded when the policy is exported for deployment.

## Where the sizes change if you change the setup

- **Network size (small / medium / large)**: only the hidden layers change. Input 48 and output 12 stay
  fixed.
- **Adding or removing an observation term (Plan 03)**: the input size changes, and old checkpoints no longer
  load.
- **Changing which joints are actuated**: the action size changes, and so does the size of the `last_actions`
  slice of the observation.

## How to verify these numbers yourself

The input and output sizes can be read from any saved checkpoint, for example
`logs/rsl_rl/quadrustand_spot_flat_baseline/<timestamp>/model_9.pt`: the shape of
`actor_state_dict["mlp.0.weight"]` is `(512, 48)` (hidden size, input size), and
`actor_state_dict["mlp.6.weight"]` is `(12, 128)` (output size, last hidden size). The observation layout
can be checked in `params/env.yaml` of a run, under the observation group `policy`.
